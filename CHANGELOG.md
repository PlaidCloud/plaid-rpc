# Changelog

## v1.16.1

- Stage the `uuid` dtype to Arrow/Parquet as a string. `DTYPES['uuid']` now declares `pandas='object'` and is Arrow-capable, so `arrow_type_from_analyze_type('uuid')` returns `pa.string()` and `pandas_dtype_from_sql('uuid')` returns `'object'`. 1.16.0 refused both (`UnsupportedDtype`), and ≤1.15.1 raised numpy's `data type 'uuid' not understood`, so a Parquet remote import of any Postgres table with a uuid column failed. `bitmap`, `geometry` and `geography` are still refused; `json` is unchanged (`pa.json_()`, string storage). **Downstream tests that pin `uuid` as having no pandas form need updating on the bump** ([@inviscid](https://github.com/inviscid)).
- Cap `SQLAlchemy<2.1`. SQLAlchemy 2.1 renamed `ORMSelectCompileState`, which `snowflake-sqlalchemy` imports, so a fresh install of `plaidcloud-rpc[full]` failed at import ([@inviscid](https://github.com/inviscid)).

## v1.16.0

- Stop `use_decimal_type` from turning the `double` and `float` dtypes into decimals ([sc-30354](https://app.shortcut.com/plaidcloud/story/30354)), a regression from [sc-30345](https://app.shortcut.com/plaidcloud/story/30345) that blocked the 1.16.0 release. `arrow_type_from_analyze_type` staged a decimal whenever `use_decimal_type` was set **and the pandas dtype was `float64`**. Before sc-30345, `double` and `float` were absent from `_PANDAS_DTYPE_FROM_SQL` and passed through as the literal strings `'double'`/`'float'`, so that test never matched them and they reached `from_numpy_dtype` as `pa.double()`. Routing through `DTYPES` gave both a declared `pandas='float64'`, and the predicate swept them in: `decimal128(38, 10)` for two genuine IEEE floating-point types. A decimal schema over a column of Python floats is not writable — `pa.Table.from_pylist` raises `ArrowTypeError: int or Decimal object expected, got float` — which took 16 of plaid's ERP physical-landing tests red. **This is more than a restored behaviour: it prevents silent numeric corruption.** `table.py`'s landing path reaches this from `sap_driver.py`, where SAP `FLTP` columns land as the literal dtype `'double'` with `use_decimal_type=True` hardcoded, and `landing_dtype`'s own docstring states the landed type must be "never DECIMAL(38,10), which would round 1.23E-15 to 0 and overflow at 1E+30" -- exactly what master was doing to them. The branch now tests an explicit `_DECIMAL_DTYPES` set (`numeric`, `decimal`) instead of a pandas dtype, so a dtype is staged as a decimal by being named, never by happening to be float64; `currency` is unaffected, still `decimal128(18, 4)` regardless of the flag. `serial` and `bigserial` keep sc-30345's fix — `int64` where master raised numpy's `TypeError: data type 'serial' not understood`. A parametrised matrix now pins all six at **both** values of `use_decimal_type`; sc-30345's own tests pinned the `False` column only, which is why this shipped ([@inviscid](https://github.com/inviscid)).

- Declare `varchar`, `geometry` and `geography` joinable as key again ([sc-30348](https://app.shortcut.com/plaidcloud/story/30348)), correcting a second [sc-30345](https://app.shortcut.com/plaidcloud/story/30345) declaration that did not match the effective prior behaviour. `joinable_as_key` was mirrored from `frame_join_multi_validator._DTYPE_ENUM` — but that enum is only `_dtype_ok`'s **fast path**: the gate then falls back to accepting anything `sqlalchemy_from_dtype` resolves, so the effective admission was `_DTYPE_ENUM ∪ {everything that resolves}`, and `varchar`, `geometry` and `geography` were all accepted through the fallback. Mirroring the enum alone flipped all three to refused. That validator runs at **execute** time, not save time, so a workflow joining on a `varchar` column and saved before the deploy would have started failing on its next run. All three are declared back to the effective set, and the registry comment now says the axis mirrors the gate's effective admission rather than naming one data structure. `bitmap` stays un-joinable — it is the one declared dtype the fallback also refuses — and `vector` stays un-joinable because it postdates the gate and has no prior behaviour to preserve. **No live behaviour changes:** nothing reads `joinable_as_key` yet (sc-30348 is the first consumer and is unmerged), so this only stops a declaration we already know is wrong from shipping. A test now pins join-key admission across the whole declared vocabulary, computing the fallback half rather than restating it, so a narrowing cannot pass silently again. Whether a `geometry` column *should* be a legal join key is a separate deliberate decision, not made here ([@inviscid](https://github.com/inviscid)).

- Declare the `vector` dtype: a float32 embedding column, StarRocks only ([sc-30352](https://app.shortcut.com/plaidcloud/story/30352)). Declared *into* sc-30345's admission boundary rather than wired through it — one `DTYPES` row, two `_ANALYZE_TYPE` rows, one `_sqlalchemy_from_dtype` row and `PlaidVector`, with no change to `_resolve`, `admit_dtype`, `require_dtype_capability`, `pandas_dtype_from_sql`, `sqlalchemy_from_dtype` or `_key`. **Dimension is column metadata enforced at write time, not part of the dtype**, so one unparameterized `vector` covers every width and `vector(768)` is refused.
  - **`PlaidVector` emits `ARRAY<FLOAT>` on StarRocks and refuses every other dialect**, deliberately breaking the house pattern where every other `Plaid*` type degrades to its base `impl`. A vector landing as VARBINARY or text is a *wrong* column, not a lesser one, and would be discovered only once a similarity query returned nonsense. `ARRAY<FLOAT>` is the measured-correct representation: on StarRocks 4.1.3 an Iceberg `ARRAY<FLOAT>` column round-trips bit-exact IEEE-754 float32 at 768 and 1536 dimensions, keeps an empty array and NULL distinct, and native Parquet unload emits a spec-conformant `LIST<float>`. The refusal is not confined to DDL — SQLAlchemy calls `load_dialect_impl` while compiling a SELECT too, so `str(select(vector_col))` raises, and a bare `str(query)` raises on the `'default'` dialect, whose message names it for what it is rather than leaving a reader hunting for a 'default' engine. `PlaidGeometry`/`PlaidGeography` are the only precedent for refusing at all, and they raise a bare `NotImplementedError` behind a class-level `# pragma: no cover` that nothing pins; this refusal is named, catchable and carries the dialect.
  - **`UnsupportedDtype` gains a third refusal shape, `dialect`.** Reporting `capability='sqlalchemy'` here would contradict `DTYPES['vector'].sqlalchemy is True` — the unavailable thing is the engine, not the capability. The three are told apart by the attributes: an undeclared dtype carries neither `capability` nor `dialect`, a declared dtype that cannot do something carries `capability`, and a declared dtype with no representation on an engine carries `dialect`.
  - **Inference matches the type string a StarRocks `ARRAY<FLOAT>` column actually compiles to.** `_ANALYZE_TYPE` maps `array<float>` to `vector`; `ARRAY<DOUBLE>`, `ARRAY<INT>` and nested element types deliberately do **not** match, so they keep being refused rather than silently becoming vectors, and bare `array` stays `text` because it carries no element type. The `^vector$` row is repointed from `text` to `vector` in the same change, so `analyze_type` agrees with `admit_dtype` instead of contradicting it. `vector` is therefore the one dtype `analyze_type`'s range gained after the original 13.
  - **A fix that falls out of the same change:** `arrow_type_from_analyze_type` now resolves its input before branching, where it used to test the raw spelling. Its branches always compared canonical dtypes, so a source spelling that resolved to a special case was admitted and then fell through to the generic pandas path — `ARRAY<FLOAT>` (the literal string reflection feeds in, and the whole reason the new regex row exists) was staged to Parquet as `string()` instead of `list<float>`; `date(%Y)` gave `timestamp[s]` instead of `date64`; `bson` gave `string()` instead of `json_()`. All three are fixed by the one line and all three are now pinned; no other dtype's arrow type moves ([@inviscid](https://github.com/inviscid)).


- Add a fail-closed dtype admission boundary: one registry of the canonical analyze dtypes, with declared per-dtype capabilities, and one named error every refusal comes back as ([sc-30345](https://app.shortcut.com/plaidcloud/story/30345)). The four dtype converters in `type_conversion.py` used to fail in four different directions on a dtype nobody had handled — `analyze_type` raised a bare `Exception`, `pandas_dtype_from_sql` **returned the input string unchanged**, `arrow_type_from_analyze_type` surfaced numpy's `TypeError: data type 'uuid' not understood`, and `sqlalchemy_from_dtype` let a `RegexMapKeyError` out with no message. So there was no single behaviour to rely on, and no way to tell whether a dtype had been fully added; `plaid` grew three separately-maintained copies of `try: analyze_type(dtype) / except: return 'text'` around it. All four now refuse through `UnsupportedDtype`, carrying the dtype, the capability refused and the context that asked: `dtype 'bitmap': declared but not sqlalchemy-capable (asked by sqlalchemy_from_dtype)`.
  - **`UnsupportedDtype` is deliberately not a `KeyError`.** `RegexMapKeyError` is one, which is exactly how `analyze_type`'s own `except KeyError` swallowed it — and how roughly six wrappers across `plaid` and `plaid-utilities` still coerce an unrecognised dtype to `'text'`. A boundary that fails into a silent default is not fail-closed, so the new error subclasses `ValueError`. `RegexMapKeyError`'s own `KeyError` parentage is untouched: other repos rely on it.
  - **`DTYPES` is the canonical OUTPUT vocabulary** — the 24 dtypes a column may carry — kept explicitly separate from `_ANALYZE_TYPE`, which is the INPUT direction (source-system type spelling to canonical dtype). Conflating the two is why the `r'^vector$'` entry in `_ANALYZE_TYPE` looked like it declared a vector column type when it only ever described a source spelling. Each declaration states `pandas`, `arrow`, `sqlalchemy`, `joinable_as_key`, `aggregatable`, `default_agg` and `profilable`; the defaults describe an ordinary scalar column, so a row states only where a dtype differs. `admit_dtype(dtype, context)` returns a declaration or refuses, and `require_dtype_capability(dtype, capability, context)` refuses unless the declaration allows what the caller is about to do.
  - **Declarations reproduce today's behaviour, warts included**, so nothing existing changes: `default_agg` mirrors plaid's `table_explorer_common.agg_type()` (which groups only text/boolean/date/timestamp/time, leaving interval/json/uuid/largebinary defaulting to `'sum'`), `profilable` mirrors `table.py`'s `_PROFILE_*` sets, `joinable_as_key` mirrors `frame_join_multi_validator._DTYPE_ENUM`, and `aggregatable` mirrors the client's `ANALYZE_NUMERIC_DATA_TYPES`. Tests bind each of those sets to the registry, so a dtype cannot be half-added again and another repo's hand-kept enum can be pointed at `DTYPES` rather than re-typed.
  - **`_PANDAS_DTYPE_FROM_SQL` is deleted**, not replaced: the registry plus `_ANALYZE_TYPE` answers everything that table answered, and keeping both would have been the same vocabulary written down twice. Every spelling it handled still resolves to the same pandas dtype, and several that it silently passed through now resolve instead of producing a string pandas rejects — `double precision`, `bytea`, `char(36)`, `serial` and `bigserial` among them.
  - **Breaking for out-of-tree callers:** `pandas_dtype_from_sql` is published API and was a total function — it returned something for every input. It now raises. A dtype no vocabulary declares raises, and so do the four dtypes with no pandas representation (`uuid`, `bitmap`, `geometry`, `geography`), rather than handing back their own name — which was never a pandas dtype and crashed later inside pandas, naming neither the column nor the dtype. This is not deferred behind a pin for every consumer: **`plaid-utilities` requires `plaidcloud-rpc>=1.11.0` with no upper bound** and holds the only live caller (`plaidcloud/utilities/query.py`, which stringifies a column's SQLAlchemy type and feeds the result to `pd.read_csv(dtype=…)`), so it absorbs this on its next build. Every dtype reachable there is either unchanged or a strict fix — `CHAR(36)` and `BLOB` previously produced strings pandas rejects — and the DDL round trip for all 24 dtypes is pinned by test.
  - **Behaviour change:** a **missing** dtype is now refused. `str(None).lower()` is `'none'`, which `_ANALYZE_TYPE` declares as text, so `analyze_type(None)` used to return `'text'` — a half-added column silently became a text column. `arrow_type_from_analyze_type` refuses the four unrepresentable dtypes by declaration instead of by numpy `TypeError`, and now normalises its input before branching, so `'DATE'` yields `date64()` rather than a timestamp. `analyze_type` raises `UnsupportedDtype` in place of a generic `Exception`, and narrows its `except KeyError` to `except RegexMapKeyError` so it can no longer swallow an unrelated lookup failure ([@inviscid](https://github.com/inviscid)).

- Add `SimpleRPC.call_rest(http_method, path, params=None, body=None)` for calling the PlaidCloud REST API ([story 29203](https://app.shortcut.com/plaidcloud/story/29203)). It sends to `/rest/v1/<path>` on the host of the connection's JSON-RPC URI, using the same token or token provider, TLS verification, proxies, headers, retries, cancellation check and trace context as JSON-RPC calls. A JSON body comes back decoded, and an empty one as `None`. Anything but a 2xx raises `RPCError`, with the HTTP status as `code` and the server's message in the text, so code that already handles RPC failures handles these too; redirects are not followed, so a 3xx raises rather than reading as an empty response. `RPCRetry` now also retries GET, PUT and DELETE, so REST calls through the shared session retry the way JSON-RPC calls do; JSON-RPC only sends POST, so its behaviour is unchanged. Also drops an unused `packaging` import from `jsonrpc.py` ([@rad-pat](https://github.com/rad-pat)).

## v1.15.0

- Send a JSON-RPC request id that identifies the call, so the server's `Start`/`Finish` log lines can be paired ([sc-24106](https://app.shortcut.com/plaidcloud/story/24106)). `http_json_rpc` stamped `assoc(json_data, 'id', 0)` on **every** outgoing request, overwriting whatever the caller supplied — so every call `SimpleRPC` has ever made arrived as id `0`, and a tenant's log is a wall of `Start "analyze/workflow/is_running" 0` / `Finish ... 0` that cannot be matched up, interleaved across concurrent calls and across pods. The client now generates an id only when the caller didn't supply one (`next_call_id()` in `rpc_common`: a per-process prefix plus a counter, e.g. `9241bf1a-17`). The prefix is load-bearing — one RPC server takes calls from many workflow-runner and app pods, so a bare counter would collide across them and leave the pairing just as ambiguous. It is fixed at import, which covers `spawn` and `forkserver`; an `os.register_at_fork` hook re-prefixes a child so a bare `os.fork()` can't hand siblings the same prefix *and* counter position either. An id is still always sent, including on `fire_and_forget`, because the server treats a missing id as a notification and answers nothing. `DirectRPC`'s own log sequence — a bare `itertools.count()` shared at class level, with the same cross-process collision — moves to the same generator, and `_create_rpc_args`' hard-coded `0` goes with it.
  - **Server-side fallback:** `execute_json_rpc` logs a `srv-`-prefixed id of its own when the request arrives with id `0` or no id at all, so the logs become pairable as soon as the RPC server is upgraded, without waiting for every client to move its pin (workflow-runner pins `plaidcloud-rpc` separately and lags). The **response** still echoes the id the client actually sent — only the log line changes. **This is permanent, not transitional.** Two request shapes can never name themselves: a spec-legitimate notification, which carries no id by design; and `plaidlink`, which pins 1.7.2 *and* hand-builds its `{"id":0}` payload as a string posted with bare `requests` (`startup_diagnostics.py`), so no pin bump of this library will ever reach that call site. Don't delete the fallback later as spent scaffolding.
  - **Behaviour change:** the request id is now a string rather than an integer. JSON-RPC 2.0 permits String, Number or NULL; no client in the fleet reads the id back off the response ([@rad-pat](https://github.com/rad-pat)).
- Unpin `setuptools`, and move the license gate to the shared Trivy action ([sc-24172](https://app.shortcut.com/plaidcloud/story/24172)). `requirements.txt` pinned `setuptools==81.0.0` — the only exact pin in an otherwise unpinned file — and because `pyproject.toml` builds `dependencies` from that file, the pin shipped as a `Requires-Dist` on the wheel. Every consumer inherited it as a resolver *conflict*: setuptools 82.0.0 removed `pkg_resources`, and no downstream project could install a newer setuptools while this pin existed, whatever its own requirements said. The pin was never about this library — nothing under `plaidcloud/` imports `setuptools` or `pkg_resources` — it was propping up `liccheck`, whose `liccheck/requirements.py` imports `pkg_resources` at module scope and whose last release was September 2023. The dependency stays, unpinned; only the ceiling is gone. `liccheck.ini` is deleted and the job is now four lines calling [`PlaidCloud/plaidcloud-github-actions/license-check@v1`](https://github.com/PlaidCloud/plaidcloud-github-actions), so the approved-license list is decided once for the organisation rather than drifting across ten copies — which it already had: the ini here authorised `gnu general public license (gpl)` while also listing `gpl` as unauthorized.
  - **Nothing about the check changes for this repo.** Trivy extracts each installed package's license and the action's `check_licenses.py` applies the allow-list, keeping liccheck's `level: cautious` semantics — an unapproved *or* undeclared license fails. Trivy's own findings surface is deliberately not used: it went empty for a 53-package venv on Trivy 0.73.0 while per-package licenses stayed correct, so a gate built on it could be disarmed by a scanner upgrade without going red. Scope widens slightly, from `requirements.txt` to a venv built from `.[full,tracing]` — the extras plaid installs in production ([@rad-pat](https://github.com/rad-pat)).

- Relax `PlaidConfig`'s all-or-nothing environment-variable gate to require only `__PLAID_RPC_URI__` and a token ([sc-23202](https://app.shortcut.com/plaidcloud/story/23202)). `_check_environment_variables` read all six `__PLAID_*` variables with bare `os.environ[...]` inside one bare `except:`, so missing any one — including `__PLAID_WORKFLOW_ID__` and `__PLAID_STEP_ID__`, which are meaningless outside a workflow runner — silently fell through to a `plaid.conf` filesystem hunt. That is why callers invented sentinel values (`workflow_id='workflow_id_not_set'`, `__PLAID_PROJECT_ID__='panel-app'`, etc.) purely to satisfy the gate. The environment path now runs when `__PLAID_RPC_URI__` and (`__PLAID_RPC_AUTH_TOKEN__` **or** a `token_provider`) are set and non-empty; the other four variables are read best-effort with `.get(..., '')`, and the `project_id` / `workflow_id` / `step_id` properties still raise at the point of use, so "not set" stays a loud error there rather than a silent fallback at construction. This unblocks sc-23191's removal of those sentinels. The outer `try`/`except` is deleted entirely — with `.get()` nothing left can raise — and the inner `urlparse` guard is narrowed from bare `except:` to `except Exception`.
  - **Behaviour change:** a process that exports both required variables **and** expects `plaid.conf` to win now flips `is_local` to `False`; `paths` / `debug` / `fetch` / `write_from_local` never populate, so `self.path(...)` raises `KeyError` and `PlaidConnection.save()` flips from a no-op to writing. `_read_plaid_conf` never exports `__PLAID_RPC_URI__` or `__PLAID_RPC_AUTH_TOKEN__`, so a local-config process cannot accidentally satisfy the relaxed gate on a second `Connect()`.
  - **Deliberate tightening:** the two required variables must now be **non-empty**, not merely present. Previously `__PLAID_RPC_URI__=''` passed the gate and yielded a broken URI with no fallback.
  - Known residual: `workspace_uuid` has no raising property (unlike project/workflow/step), so a partial environment yields a silently empty tenant id. Nothing in plaid-rpc routes on it, so it is left as-is ([@inviscid](https://github.com/inviscid)).

## v1.14.0

- Append the real cause to the friendly error text an RPC method returns ([sc-23492](https://app.shortcut.com/plaidcloud/story/23492)). `call_as_coroutine._get_error_message` computed the exception type and message and then discarded them whenever the method declared a `default_error` — which every `@rpc_method(...)` in plaid does — so the entire RPC surface could only ever return its generic string ("Exception when retrieving table metadata" and the like) and every user-reported error arrived with zero diagnostic signal by construction. The cause was only recoverable from the plaid-rpc pod logs, by someone with cluster access: [sc-23447](https://app.shortcut.com/plaidcloud/story/23447) burned a multi-hour cross-team investigation on a `TypeError` that was sitting in those logs the whole time. Failures now return `'<default_error>: <ExceptionType>: <message>'`. Stack frames still stay server-side — this keeps `format_exception_only`, matching what the `default_error is None` branch has always returned to every caller. `SyntaxError` and its subclasses are reduced to their bare type and message before being surfaced: `format_exception_only` is documented to return only the exception, but it makes an exception of the `SyntaxError` family, decorating it with `File "<path>", line N` plus the offending source line and a caret. Both are server-side artefacts — the path always, and the source line whenever what failed to compile was ours rather than the caller's — and widening the cause to every RPC method would otherwise have widened that leak with it ([@inviscid](https://github.com/inviscid)).

- Add DB/cache span instrumentation to `init_tracing` so query/command execution nests as child spans under the active RPC span. **Redis** is auto-instrumented globally (patches the client class). **SQLAlchemy** is instrumented via a global `create_engine` patch, which reaches call sites that use the module-attribute form `sqlalchemy.create_engine(...)` (what engine factories should use); `from sqlalchemy import create_engine` bindings keep the unpatched function and aren't covered. Best-effort and independently guarded, so an older `[tracing]` install without the new extras degrades quietly. Adds `opentelemetry-instrumentation-sqlalchemy` and `opentelemetry-instrumentation-redis` to the `tracing` extra ([@Mirz-Ka](https://github.com/Mirz-Ka)).

## v1.13.0

- Correct the `verify_ssl` defaults so upgrading does not change any existing connection's behaviour ([sc-23168](https://app.shortcut.com/plaidcloud/story/23168)). Configuring from explicit arguments — the API added in 1.11.0, which has no deployed callers — still defaults to verifying. The two pre-existing configuration sources now default to **not** verifying: an absent `__PLAID_VERIFY_SSL__`, and a `plaid.conf` with no `verify_ssl` key. `PlaidXLConnect` likewise defaults off, since it is a shipped desktop add-in whose installs in the field have always run unverified. 1.12.0 defaulted all of these to True, which would have turned verification on for connections that predate `verify_ssl` ever reaching the transport and would have broken any endpoint presenting an internal or self-signed certificate. Opting in is unchanged: set `__PLAID_VERIFY_SSL__='True'`, `verify_ssl: true` in plaid.conf, or pass `verify_ssl=True` ([@inviscid](https://github.com/inviscid)).
- Make `verify_ssl` a real connection option and forward it to the transport ([sc-23168](https://app.shortcut.com/plaidcloud/story/23168)): `Connect.ready()` and `PlaidXLConnect` built `SimpleRPC` without `verify_ssl`, so `SimpleRPC` coerced its own `None` default to `False` and passed it to `requests` as `verify=False`. **TLS certificate verification was therefore off on every RPC call made through `Connect`** — UDFs, Jupyter and server Panel apps — with `urllib3.disable_warnings(InsecureRequestWarning)` suppressing the warning that would have revealed it. `PlaidConfig.verify_ssl` was read from `__PLAID_VERIFY_SSL__` and then dropped on the floor. `PlaidConfig` and `Connect` now accept a keyword-only `verify_ssl`, `Connect.ready()` passes it through, and `PlaidXLConnect` takes one too. **Certificate verification is now on by default from every source** — the `verify_ssl` argument, the `__PLAID_VERIFY_SSL__` environment variable when absent, and the new `verify_ssl` key in `plaid.conf` when absent. **This is a behaviour change for any deployment that has been running unverified without saying so.** Anything addressing an internal or self-signed endpoint must now opt out explicitly with `__PLAID_VERIFY_SSL__='False'` or `verify_ssl: false`. JupyterHub already sets the variable to `'False'` in all 29 tenant values files, and workflow-runner propagates its own `'False'` into every UDF environment, so those two are unaffected ([@inviscid](https://github.com/inviscid)).

- Configure a connection from explicit arguments ([sc-21805](https://app.shortcut.com/plaidcloud/story/21805)): `PlaidConfig` and `Connect` accept keyword-only `rpc_uri`, `auth_token`, `token_provider`, `workspace_uuid` and `project_id`. Passing `rpc_uri` configures from those values alone, skipping both the six-`__PLAID_*`-environment-variable path and the `plaid.conf` file — the only option where neither is available. `token_provider` is a callable resolved per request (`SimpleRPC` already supported this), applies whichever source configured the rest, and is deliberately separate from `auth_token` so that stays a `str` for callers that format it into a header. Existing callers pass no new arguments and take the same path as before. Two supporting fixes: `_C` was a class attribute, so config built in one place leaked into every other instance in the process — it is now per-instance; and `_init_plaidcloud_config` read the raising `project_id` property, so a project-less connection could not be constructed at all — it now reads `_project_id`, leaving the property to raise at the point a project is actually needed ([@inviscid](https://github.com/inviscid)).

- Add `is_dialect_databricks_based` and extend the Plaid* type decorators for the Snowflake/Databricks lakehouse backends ([sc-23158](https://app.shortcut.com/plaidcloud/story/23158)): `PlaidNumeric` → Databricks `DECIMAL(38, 10)`; `PlaidTimestamp` → Databricks `TIMESTAMP_NTZ` (Snowflake rides the plain `TIMESTAMP` impl via session `TIMESTAMP_TYPE_MAPPING`); `PlaidUnicode` → Snowflake `VARCHAR`, Databricks `STRING`; `PlaidTinyInt` → Databricks `TINYINT`; `PlaidJSON` → `VARIANT` on both, with binds serialized to JSON strings wrapped in `PARSE_JSON` and reads parsed back to Python objects (dict-in/dict-out parity with JSONB). Vendor dialects stay lazily imported — nothing new is required at module load ([@inviscid](https://github.com/inviscid)).

- Add a `currency` analyze data type: the new `PlaidCurrency` SQLAlchemy type renders an explicit `DECIMAL(18, 4)` on every warehouse dialect (8-byte Decimal64 values on Databend), with matching pandas (`float64`) and arrow (`decimal128(18, 4)`) conversions. Type inference is unchanged — `currency` source-type spellings still map to `numeric`; only an explicitly stored `currency` dtype gets the narrow type ([@inviscid](https://github.com/inviscid)).
